# Triangle — Code Refactoring

## Зауваження до початкового коду

Під час аналізу початкової реалізації класу `Triangle` були виявлені такі проблеми:

1. **Порушення форматування коду.**
   У коді використані нерівномірні відступи, зайві пробіли та різне форматування конструкцій. Наприклад, `public  boolean  equilateral()` містить зайві пробіли. Код варто привести до єдиного стилю відповідно до Google Java Style Guide.

2. **Невдалі назви методів.**
   Методи `takeA()`, `putA()`, `takeB()`, `putB()`, `takeC()`, `putC()` не відповідають поширеним Java-конвенціям і не є достатньо зрозумілими. Для доступу до властивостей доцільніше використовувати назви на кшталт `getSideA()`.

3. **Невдала назва методу `perim()`.**
   Скорочена назва `perim()` не є достатньо очевидною. Назва `getPerimeter()` краще описує призначення методу.

4. **Недостатньо описові назви полів.**
   Назви `a`, `b`, `c` є звичними математичними позначеннями сторін трикутника, але в програмному коді назви `sideA`, `sideB`, `sideC` роблять призначення полів очевиднішим без необхідності додаткового контексту.

5. **Наявність порожнього конструктора.**
   Конструктор без параметрів створює об'єкт, у якого сторони мають значення `0`, тобто він не представляє коректний трикутник. Якщо клас повинен створювати лише валідні об'єкти, такий конструктор не потрібен.

6. **Відсутня перевірка коректності сторін.**
   Клас дозволяє створити трикутник із нульовими або від'ємними сторонами, а також із такими сторонами, які не задовольняють нерівність трикутника. Необхідно перевіряти вхідні значення під час створення об'єкта.

7. **Setter-и дозволяють перевести об'єкт у некоректний стан.**
   Методи `putA()`, `putB()` та `putC()` дозволяють змінити окрему сторону без повторної перевірки всіх сторін. Через це вже створений об'єкт може перестати бути коректним трикутником. Для цього класу доцільно використовувати незмінні (`final`) поля.

8. **Зайва конструкція `if-else` у `equilateral()`.**
   Метод повертає результат логічного виразу, але цей результат спочатку перевіряється через `if`, після чого повертається `true` або `false`. Конструкцію можна безпосередньо замінити логічним виразом.

9. **Незрозуміла та повторювана формула площі.**
   У методі `area()` декілька разів викликається `perim()`, а значення `0.5` повторюється без пояснення. Використання окремої змінної `semiPerimeter` робить формулу Герона значно зрозумілішою.

10. **Неточне порівняння `double` у `equilateral()`.**
    Порівняння `double` через `==` може давати несподівані результати через особливості представлення чисел із плаваючою крапкою. Для геометричних обчислень доцільно використовувати допустиму похибку (`epsilon`).

11. **Недостатньо зрозуміла реалізація `equals()`.**
    Параметр методу названий `o`, що не дає достатньо інформації про його призначення. Також логіку методу можна зробити читабельнішою за допомогою перевірки на тотожність об'єктів і форматування умов у декілька рядків.

12. **Надмірна змінюваність класу.**
    Клас містить відкриті методи для зміни всіх трьох сторін. Оскільки зміна однієї сторони може вплинути на валідність всього трикутника, краще зробити об'єкт незмінним після створення.

## Виконаний рефакторинг

У результаті рефакторингу було:

* приведено форматування до єдиного стилю;
* перейменовано методи та поля на більш зрозумілі;
* видалено порожній конструктор;
* додано перевірку коректності сторін;
* зроблено поля `final`;
* видалено setter-и;
* спрощено перевірку рівностороннього трикутника;
* перейменовано методи `perim()` та `area()` на `getPerimeter()` та `getArea()`;
* спрощено та зроблено читабельнішою формулу Герона;
* додано `epsilon` для порівняння сторін у `isEquilateral()`;
* покращено читабельність `equals()` та `hashCode()`;
* зроблено клас незмінним після створення об'єкта.
